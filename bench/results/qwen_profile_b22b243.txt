Harness: bench/run_bench.py (server args, -cs 65536, median of 3); rocprofv3 --selected-regions via bench/profile_region.py
(now takes --extra for model_init flags) + bench/analyze_trace.py. Raw traces and analyses: exlproject/logs/prof/qwen_*.
The b22b243 -ngr traces were taken with --hip-trace; after an OOM kill (rocprofv3 + 37 GB table in RAM, 2026-09-28 11:08)
every later trace is disk-streaming mode without --hip-trace, <= 16-32 steps (see "Memory" below).

1. Model shape (why it is not DS4)
----------------------------------
hidden 2560, 48 layers = 36 GatedDeltaNet (linear attention) + 12 QSA full attention (24 q / 2 kv heads, head_dim 256,
indexer-selected 4-token blocks past 2048 tokens), 512 experts top-10 (intermediate 640), 1 shared expert,
4 fp32 residual streams mixed by GatedResidual "low-rank hyper-connections" at 97 sites per token
(2 per layer + final mixer), PLE layer at layer 2 fed by a 36.4 GiB hashed n-gram table (16 rows x 160 dims per token).

Weight bytes per decoded token (from quantization_config.json):
  GatedResidual mix, fp16 (97 x (324 x 10240 + 10240 x 320) x 2 B)      1.28 GB   <- not quantized, untouched by every EXL3 GEMV change
  dense EXL3 GEMV: GDN qkv/z/out K5 (1.31 GB), attn q/k/v/o/indexer K6
    (0.46 GB), shared expert K5 (0.15 GB)                               1.92 GB
  routed experts, 10 x 3 x ~0.82 MB x 48 (K4)                            1.17 GB
  lm_head K6                                                            0.48 GB
  router fp16 (48 x 512 x 2560)                                         0.13 GB
  total                                                                 ~4.98 GB  -> ~23.7 ms/token at ~210 GB/s

Why Qwen is "a weirdo" (+4% from GEMV-tiles vs DS4's +26%): a quarter of its decode bytes are the fp16 GatedResidual
hyper-connection matrices, which run on their own two hc kernels (gr_dots / gr_finalize), not the EXL3 GEMV; its
EXL3 GEMVs are K5/K6 (dense) and K4 (experts), already near the bandwidth roof before GEMV-tiles; and its 12 attention
layers run a graphed Triton split kernel that was compiled without the AMD buffer-op specialization (91.5 us/call
instead of ~14). GEMV-tiles sped up the part that was already fast; the slow parts were elsewhere.

7. Ranked list (measured ms saved / effort)
------------------------------------------
  1. GatedResidual decode mix: one fn row per block, each block re-reads the 40 KB stream stack; 325 blocks with ~2.5
     dependent trips per stream. 4 rows per block, streams in registers: 60.8 -> 36.3 us/site, -2.4 ms/token.
     Prefill: the torch gate-mean tail 3.6 ms/site at R=2048 -> 0.4 ms. DONE (d365a4f), bit-identical.
  2. Graphed GQA decode attention compiled without tt.pointer_range / tt.divisibility: 91.5 -> 31.8 us/call
     (-0.7 ms/token at 512, -0.8 at 8K, -1.2 ms per MTP step). DONE (6684d1d), bit-identical.
  3. MTP verify router on hgemm (105 us x 48): multi-row router GEMV, 40 us; -3.1 ms/step. DONE (6684d1d); MTP greedy
     now token-identical to plain greedy.
  4. Paged prefill attention at head_dim 256 spills: 1-stage 128-row tile, kernel 2-3x (up to 3x at 16K past); e2e
     pp2048 +1.8%, Gemma pp2048 +4%. DONE (this branch, EXL3_ROCM_PREFILL_HD256).
  5. (not done) GR hc_apply folded into the next site's gr_dots (as DS4's HC_FUSE): 96 launches, ~0.45 ms/token.
  6. (not done) GR prefill matmuls on hipBLAS at 17-25 TF (54 ms/forward): the WMMA backend needs a row-major B, i.e.
     transposed copies of proj/up (+1.3 GB) -- memory the -ngr/-ngl budget does not have.
  7. (not done) Decode gaps 4.1 ms/token (1498 launches); GDN in_proj / ba / conv / recurrent fusion is the lever.
  8. (not done) GDN chunked prefill (vendored fla recompute_w_u spills 1608 B): autotuned; upstream-vendored code.
